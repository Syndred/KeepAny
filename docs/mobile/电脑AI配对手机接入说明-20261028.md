# 电脑 AI 配对手机接入说明（2026-10-28）

本说明针对 **电脑上的本地 Codex / Claude Desktop → 本地 stdio launcher → 手机前台 HTTPS MCP**。代码和可执行 launcher 已具备；真实官方 SDK 与 Android AVD 纵链已有证据，**真正 Codex / Claude Desktop 的界面接入仍待执行**。初次 readiness 仅只读；后续补做了自有 loopback 合成手机协议与真实终端 C，见文末。没有修改用户全局配置、连接设备或向模型发送资料。

## 先准备电脑与资料范围

- 电脑需要可用的 Node.js `>=20.19.0` 及完整 KeepAny MCP launcher 安装目录，不能只复制 `.mjs` 而遗漏运行依赖。当前本机冻结程序为 `dist/mcp-launcher/bin/keepany-mcp.mjs`，SHA256 `126e30da08cae9c756e4d292a68a0af56f2d0414bef15792ca3d51fce2a5eea1`；包是本机技术验证产物，未发布 npm，也没有 Claude `.mcpb` 一键扩展。
- 先用一条合成项目、仅可读 `name`、不开放写入测试。MCP 返回授权资料 ID 和选中的普通字段；KDBX 密码、主密码和恢复码不属于该接口。工具结果会进入所选 AI 的会话，本地 TLS 不代表 AI 收到的结果永远只留本机。
- 手机与电脑之间须有可达网络。手机填写自己的私有 IPv4 地址，配对文件已包含对应端口、证书和 pin，不能手改地址或关闭 TLS 校验。手机 `127.0.0.1` 不等于电脑 `127.0.0.1`；只有已明确建立同端口转发时才能按该地址接入。物理 LAN / 路由器隔离尚未实测，不能拿 AVD 的 ADB 转发作为 LAN 通过证据。
- 配对文件和后续连接文件含临时凭据，只保存在可信电脑的新私有目录，不粘贴到 AI 对话，不作为普通附件上传。POSIX 要求当前用户、文件 `0600`、父目录 `0700`；Windows 要求受保护的独占 DACL（当前用户完整权限，允许 SYSTEM，不能有其他主体或普通继承权限）。普通 Downloads 复制文件通常不满足此条件；启动器会拒绝，不自动替用户 chmod / 改 ACL。目录链不可为 symlink / reparse point，文件须为单硬链接普通文件。

## 第一阶段：终端配对，手机明确批准

1. 手机上打开“助手访问”，选择资料、可读 / 可写字段和 5 / 10 / 15 分钟授权时长，输入手机实际本机地址。
2. 点击“准备配对文件”，通过系统导出并确认文件保存；回 App 后再明确点击“开始等待电脑”。仅打开分享窗口不表示监听已启用。票据从准备时起两分钟过期，准备、导出和启用沿用同一 endpoint / pin。
3. 把**本次唯一配对文件**安全复制到电脑私有目录。手机保持 App 前台，不切到其他 App 或锁屏。电脑终端启动（下面路径均须换成真实绝对路径；示例不是已执行命令）：

   ```powershell
   & 'C:/ABSOLUTE/node.exe' 'C:/ABSOLUTE/mcp-launcher/bin/keepany-mcp.mjs' --mobile-pairing 'C:/PRIVATE/KeepAny/mobile-pairing.json'
   ```

4. 电脑 stderr 显示八位核对码；手机弹出电脑请求。核对客户端、两端相同核对码、资料 / 字段 / 时长，再由手机明确批准。不一致或不想连接时拒绝。当前 launcher 声明的客户端名固定为 `KeepAny MCP desktop`，不是对上游 Codex / Claude 品牌的身份认证。
5. 成功后终端显示一个随机命名的私有 `connection-UUID.json` **路径**。等待该路径出现后，记住路径，再用 Ctrl+C 关闭本次终端 CLI。当前实现关闭电脑 CLI 只断连接，不代替手机撤销；连接文件保留，可供下一阶段同一手机前台会话重连。文件内容不要复制出来。

先终端配对是现有实现可组织的推荐步骤，不是新协议：`launchMobileMcp` 在完成手机批准、真实远端 SDK 握手和工具白名单核验后，才写 profile 并启动 stdio。直接让桌面 AI 启动 `--mobile-pairing` 会让 MCP 初始化等待人工审批；Codex 官方文档当前默认启动超时为 10 秒，存在提前超时风险。[Codex MCP 配置](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)

## 第二阶段：桌面 AI 用连接文件重连

### Codex 本地 MCP

本机 `codex mcp --help` / `codex mcp add --help` 已确认支持 stdio command / args；本机 CLI 为 `0.164.0-alpha.11.1`。以下是 **供操作者之后录入**的示例，尚未写入或运行。可放到已信任独立项目的 `.codex/config.toml`，或在本机 MCP 设置中提供同样的命令 / 参数；不要覆盖用户已有配置。

```toml
[mcp_servers.keepany_mobile]
command = "C:/ABSOLUTE/node.exe"
args = ["C:/ABSOLUTE/mcp-launcher/bin/keepany-mcp.mjs", "--mobile-connection", "C:/PRIVATE/KeepAny/connection-UUID.json"]
startup_timeout_sec = 30
enabled = true
```

这里的 30 秒只是该桌面 server 的初始化预算，不延长手机票据 / 授权或 launcher 的单请求截止。Codex 官方配置支持本地 stdio、项目级 MCP 配置及启动超时；具体桌面设置界面与组织策略仍需在实际版本中验证，不能将本机 CLI 帮助当桌面 UI 已通过。[官方配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)

### Claude Desktop 本地 stdio

使用 **本地开发者 MCP 配置**，不是云端“添加远程 connector”。将下列 server 合并到现有 `mcpServers`，不要覆盖其他 server；按桌面版本要求重新启动并检查本地 MCP 状态。

```json
{
  "mcpServers": {
    "keepany-mobile": {
      "command": "C:/ABSOLUTE/node.exe",
      "args": [
        "C:/ABSOLUTE/mcp-launcher/bin/keepany-mcp.mjs",
        "--mobile-connection",
        "C:/PRIVATE/KeepAny/connection-UUID.json"
      ]
    }
  }
}
```

Claude 的本地配置入口、JSON command / args、配置后重启和本地连接状态见 [MCP 官方本地客户端指南](https://modelcontextprotocol.io/docs/develop/connect-local-servers)。新版 Desktop 也可能采用 Extensions / Local MCP servers 页面，组织策略可能禁用本地 MCP；本仓库当前没有 `.mcpb` 扩展包。[Claude 本地 MCP 官方说明](https://support.claude.com/en/articles/10949351-getting-started-with-local-mcp-servers-on-claude-desktop)

不能把手机私网自签 URL 直接填进 Claude 云远程 connector：该机制由 Anthropic 云发起请求，不是电脑本地网络连接。现 launcher 的局部证书信任、正常 IP SAN、SPKI pin 与私有 profile 都不由该云配置替代；本方案没有公网 relay。[Claude 远程 connector 的官方网络边界](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)

## 真正桌面接入时要逐项核对

1. 桌面客户端确实显示四个工具：`list_assets`、`get_asset`、`preview_asset_update`、`confirm_asset_update`（客户端可能添加 server 前缀）。首次只请求“列出本次授权合成项目的名称，不修改”；只出现选中记录的 ID / name，未选记录和字段应拒绝。
2. 另开明确包含 `name` 写权限的手机授权，先预览一次合成改名。在手机逐批批准前，confirm 必须拒绝；手机拒绝也不得写。手机批准后再明确确认一次，同 operation / preview 重复应幂等，正式详情可见同 ID 的变化。桌面自己的许可不能代替手机批准。
3. 手机撤销先取消，读仍有效；确认撤销后旧 client / profile 均应拒绝。后台、锁屏、停止或重启连接后旧 profile 不应自动恢复；新 start 证书会轮换，必须新配对，不自动接受新 pin。
4. 若读写结果不确定，先在手机核对实际记录与审计，不自动重复写。不要仅凭桌面显示“Connected”就认定范围、逐批批准、撤销或落盘已通过。

## 补验：真实终端无父 initialize → profile → 重连

这是 **Windows C、真实打包 CLI + HTTPS socket + 受控合成手机协议**。复用正式 `createMobileMcpPairing`、MemoryAuthority、既有合成证书 fixture；只有一个合成项目、read=`name`、write=[]。批准来自受控 trusted fixture 命令，**不是 Native 手机 UI，也不是 Codex / Claude Desktop**。不改产品 / launcher bytes，仍为上述 `126e…eea1`；测试显式使用该 executable，跳过 `beforeAll` 的 rebuild。

| 实际操作 | 实际结果 |
| --- | --- |
| 真 ConPTY 启动 `--mobile-pairing`，没有 SDK 父 client，没有向 stdin 发 initialize | 出现公开码 `4BBF94A8`，fixture 同码；批准前 profile=0、grant=0、手机侧 MCP initialize=0 |
| 受控 trusted 批准，仍不给下游 initialize | CLI 在 stderr 给出私有 profile 路径；strict reader 验证同 grant、name 只读；手机侧 upstream initialize / tools-list 各1。无需下游 initialize 就已经写完 profile |
| 真 PTY Ctrl+C | 被动 observer 记录 SIGINT 事件1、Node exitCode130；ConPTY PowerShell 壳自身返回1，两者分开记录。没有用 Windows `child.kill('SIGINT')` 冒充信号 |
| 同 profile 真终端启动 `--mobile-connection`，仍不发父 initialize | 手机侧 upstream initialize / tools-list 累计各2、原 grant 仍活跃；再 Ctrl+C 同样实际 SIGINT1 / Node130 |
| 两个终端都退出后，官方 SDK 新父 client 用同 profile 重连 | 四工具准确；只读选中项目 ID / name、未选 ID 拒绝，writes=0。先前终端不曾接收下游 initialize，不影响后续正式 SDK 初始化 |

首轮控制器由 plain exec 启动，工具关闭了其 stdin，批准命令无法送达；当时只到 pending、没有批准或 profile，是**工具前置失败**。保留首轮码 `94132D46` 与 Ctrl+C SIGINT1 / Node130 记录；精确结束自有 fixture PID 后，换成 PTY 控制器执行上表。没有将其当成配对产品失败或静默重试已批准事务。

另新增可重复回归到 `apps/mcp-launcher/src/mobile-launch.test.ts`：不创建 SDK 父 client，不向原始 child stdin 写任何 bytes；批准后 profile 已存在且 strict 可读、stdout bytes=0，再通过真实 stdin EOF 关闭 CLI，Node 正常 exit0 / signal=null、grant 保留；官方 SDK 再用该 profile 完成四工具 / exact ID+name 投影 / 未选 ID 拒绝。**EOF 与 ConPTY SIGINT 是两条分开的实测，未互相替代。**
