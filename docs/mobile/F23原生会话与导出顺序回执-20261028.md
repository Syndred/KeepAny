# F23 原生会话与导出顺序

## 为什么分成准备和激活

正式系统文件保存/分享会改变应用前台状态；把“启动前台MCP→系统导出ticket”串起来，会因pause停止刚启动的listener。本片把顺序定为：生成短期配对文件→显式系统导出→返回应用后另点开始等待。准备态仅保留两分钟内存身份，激活须使用完全同一instance/endpoint/证书/SPKI；端口被占时失败并重新生成，不偷偷变更导出文件对应的地址或pin。

TypeScript `prepareNativeMcpTransport` 已接这两阶段合同，Native activate返回四元组逐字比对；元数据准备不调用start/activate或handler。关闭跨越在途activate也会停止对应实例，错port/pin/instance不创建handler。普通启动reset仍负责清旧WebView孤儿状态。

## 会话编排

`prepareNativeMcpSession` 固定一次canonical store/dataset上下文；私有authority必须先能正常读取才允许分配Native准备态，失败不回退Memory/普通SQL，错误只固定码。准备时创建同一配对ticket，激活时才把它接到真实HTTP桥，避免导出后又生成不同nonce/secret。

模型仍经原四工具、手机scope确认及逐次preview批准。UI预览保留在内存，私有authority只保hash/元数据；批准前重新读取同canonical store和version/before字段。资料集失效/Native停止立即使commit guard失败，停止与持久撤销确认区分；不确定写receipt保留pending，不自动重放。

自review补了两项：context在Native prepare尚未返回时失效，既有close可能已结束，必须继续清掉晚分配的准备态；初始store读取错误统一脱敏。另对持久撤销失败允许明确重试，同时Native IO已停止，不伪报授权撤销已确认。

- 新会话5C、桥13C、配对6C共24通过/0失败/跳过，`test-results/native-mcp-session-final.json`；类型与定向lint通过。
- 会话C真实使用原McpAuthority/配对HTTP/官方SDK，Native IO替身：准备无grant/未激活、canonical dataset参数、显式激活/手机批准、SDK只读与预览、版本变化拒批、审计/关闭撤销、private store先失败、资料集失效晚prepare清理、后台停止、撤销失败与显式重试。不是OS桥/手机界面证明。

本片尚未注册Native会话工厂到React，也未启用连接卡片；正式UI继续准确不可连接。没有新端口/设备/普通或秘密资料操作。
