# MCP 便携 HTTP 协议纵切（未接原生监听器）

日期：2026-10-27。这是后续 Native 接入的协议/授权组件，不是 F23 原生全功能完成回执。当前 App 的准确不可连接提示保持；本片没有打开端口或新增资料接收方。

## 实现与合同

复用已安装的官方 `@modelcontextprotocol/server`/`client` 2.1.0、现有四工具、权限白名单、逐次批准与 CAS。使用官方 `createMcpHandler` 处理 Web Request/Response 与协议兼容；不手写 JSON-RPC。[官方 Web-standard 指南](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/serving/web-standard.md)

新增 `http-handler.ts` 不签发或批准 grant，只接受已有有效 Bearer 授权；严格固定 endpoint、真实 Host 与明确 Origin 集合，拒 Cookie，不提供批准/签发 HTTP 路由。最多4个请求，每次30秒，SDK读取正文最多1,000,000B，响应累计最多8MiB；关闭或取消后不再释放结果/继续写入。写入仍经过真实存储的每次尝试守卫，已提交后丢响应保留 pending，不自动重放。

**实际浏览器发现**：标准 Browser Request 会丢弃禁止设置的 Host 头。不能用发布地址替代实际入站 Host，否则无从验证重绑定。原生 HTTP parser 必须把捕获的 Host 作为单独入站元数据交给适配器；缺失、矛盾或不匹配均拒绝。已用实际 Chromium 检查 `request.headers.get('host') === null`，不是凭 Node 行为推断。

## 最低 WebView API 的补验

当前应用最低WebView111，而[维护者兼容数据](https://github.com/mdn/browser-compat-data/blob/main/api/Response.json)记录静态`Response.json`从Chrome115才有。已实际在隔离Chromium删除该静态方法后执行同SDK链，原出现`Response.json is not a function`；不是把User-Agent改旧就称真旧WebView。

按[Fetch标准](https://fetch.spec.whatwg.org/#dom-response-json)的序列化、JSON默认Content-Type和原生Response构造步骤补缺失方法，仅在不存在时安装；已有实现及fetch保持原样，未复制上游实现代码。类型无效/BigInt/204有body等仍由JSON或原生构造器拒绝，自定义Content-Type保留。相关9C以及实际浏览器“正常API/缺方法”两条件2.2秒均绿；`mcp-http-compat-final.json`、`mcp-http-browser-legacy-red.log`/`green.log`。这是受控API缺失B/C，不宣称实际WebView111/iOS16.4已装机验证，原生接入仍未完成。
