## 安全审查与实际执行

执行前完整只读审helper，Native方法只允许本case的exact fresh UUID DB名、readonly=false及固定白名单；没有全局connection-consistency/closeAll/deleteDatabase。factory和exists是会计数的受控stub，factory若被调用立即固定失败；实际均0。生产类通过专用真实Native SQL adapter调用，BEGIN/COMMIT/ROLLBACK映射专用SDK方法，execute/run均transaction:false。

三组名称先在OS确认main/-wal/-shm均missing，helper再以Native isDatabase确认不存在，才createConnection/open。诊断fixture只在自己的库建立控制schema、额外canary表、两条dataset元数据和一条prepared restore元数据，没有生成它们所引用的业务数据库。fixture里的keepany-v1字面标签不是对真实keepany-v1的操作。

各fixture先构造并commit，再显式设目标user_version、取得完整before逻辑快照，之后调用同生产类open。77是在该fixture的已开连接上设版本后测试manager.open，不是从App全新生产driver打开现有77库；SDK首次open未来库与完整启动UI不在本片覆盖。

整个原helper一次调用约 907.5ms（含三fixture创建、Bridge读写、guard和关闭），不是App启动/性能指标。没有人为重试。helper无Native-call硬取消；实际本次完整返回，未使用Promise.race掩盖在途I/O或把观察超时当取消/closeACK。
