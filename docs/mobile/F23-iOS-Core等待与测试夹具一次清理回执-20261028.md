## 具体源码风险

修前 `Tests/KeepAnyMcpTransportCoreTests/TransportTests.swift`：

1. `TLSProbe.init` 在140行赋值最后未初始化的 `channel`，147行等待真实TLS握手。
2. 握手验证或deadline在赋值后失败，会进入catch，159–160先关闭channel并shutdown group，随后throw原错误。
3. 对完全初始化后的失败，若Swift运行 `deinit`，188行又提交新的 `channel.close().wait()`，190行再向已关闭loop提交新任务并wait。原deadline此时也已无运行的loop，不能替这些新future提供超时。

固定版本 [NIO2.104 ChannelPipeline.close](https://github.com/apple/swift-nio/blob/2.104.0/Sources/NIOCore/ChannelPipeline.swift) 在线程外通过eventLoop.execute排队；[SelectableEventLoop](https://github.com/apple/swift-nio/blob/2.104.0/Sources/NIOPosix/SelectableEventLoop.swift) 无法排队时可以丢弃execute任务；[EventLoopFuture.wait](https://github.com/apple/swift-nio/blob/2.104.0/Sources/NIOCore/EventLoopFuture.swift) 本身没有独立wall-clock截止。因此在已关闭loop上新建close/submit future后同步wait有明确无界风险。

[Swift compiler初始化文档](https://github.com/swiftlang/swift/blob/main/docs/FailableInitializers.md) 描述完全初始化后失败会调用用户deinit；但[官方论坛SR-13355记录](https://forums.swift.org/t/deinit-and-throwing-initializers/38871)也出现过早期throw分支影响析构的历史差异。**本轮Swift6.2是否实际进入这条二次清理，仍需阶段日志或真实stack确认**，不能用语言规则推论冒充本轮实锤。

## 实际变更

- 仅修改 `apps/mobile/ios/KeepAnyMcpTransport/Tests/KeepAnyMcpTransportCoreTests/TransportTests.swift`，新增私有 `ProbeCleanup`；生产Sources、Package.swift、Prepare测试、UI测试、workflow与业务限额均未改。
- cleanup owner在 `channel` 尚未初始化前创建，catch只使用局部owner；不会调用部分初始化self的helper。
- catch和deinit共用同一个owner。加锁标记started后才做首次NIO清理；任何第二入口只输出skip，不会再提交close/submit。早期失败也由catch明确清理，不依赖Swift是否调用deinit。
- 首次清理在仍运行的loop上settle未完成promise，再关闭已记录channel、shutdown group；settle或shutdown明确抛错会记录测试失败，不能当清理完成。正常已关闭channel的close错误仍保留脱敏stage，不改变原TLS错误断言。
- stderr立即输出固定phase和非秘密随机probe ID：初始化、TCP已连、握手前后、catch诊断前、cleanup前后、settle/close/shutdown前后、deinit进入/退出或重复skip、write/reply前后/失败。新stage不含请求、endpoint、证书、body或key。
- 保留全部17个测试入口。既有 `testInitializerFailuresCompletePromiseBeforeShutdownAndNextProbeConnects` 在原SNI/坏PEM早期失败后，增加真实未信任TLS的晚期失败，仍要求其NIOSSLError/NIOSSLExtraError类型，再执行原正常TLS探针。没有增加skip、接受timeout、降低SAN/零字节/30秒/8MiB断言。
