## 执行批次与最小检查

1. M0先检查原生插件、持久目录、事务/文件失败、KDBX加密和实际备份；Android/iOS真机条件分开。
2. 每个实现切片只运行相关仓库/领域测试和受影响真实UI路径，加一个关键失败/取消路径。首次通过后，无代码变化、失败或新风险不重复全量。
3. 23组按“核心CRUD与密码/图→工作流费用待办→导入和回收站→备份迁移→受控连接器/AI/MCP”分包。每个子代理明确文件和环境所有权，不覆盖别人的改动。
4. 实现完成后冻结候选，执行一次集中核心链与必要兼容/敏感边界回归。最终包变更后，只重验受影响项及包身份/启动；不把旧候选证据冒充新候选。

当前Web定向测试很多使用`/@fs`开发模块或IndexedDB夹具。迁到手机时应复用领域断言、输入样本和真实UI步骤，替换为实际原生仓库回读；不能只把浏览器视口改390就称Native测试。不能在发布应用添加只为测试存在的秘密导出入口。

## gstack QA采用的方法

使用已安装的[gstack QA](C:/Users/Administrator/.codex/skills/gstack-qa/SKILL.md)及其`sections/scope.md`、`sections/system-functional.md`中的范围/隔离/合同取证原则。本子任务是静态合同编写，未启动产品探测或浏览器，不产生QA分数。

- 先选B/N/C/S目标并确定合成资料、端口、数据目录与下游目的地；不能因地址是localhost就假定安全隔离。
- 成功须观察最终业务效果与持久状态，不只观察按钮反馈/请求接受。功能合同结果用通过/失败/条件未具备/待执行/不确定，不用浏览器健康分替代。
- 先记录首次失败及最小复现，再修负责文件；重跑原失败步骤、必要回归和相邻成功路径，查看最终持久状态。没有服务/设备不通过放宽安全或弱化断言来“修复”。
- 真正有价值的回归才补测试：优先现有表格/夹具，记录它保护的边界、原覆盖缺口、失败原因和不证明的范围；不为可逆低影响样式改动增加镜像测试。
- 每个可回滚修复与必要回归独立提交。保留红/绿证据；未经复验的修改不能标“已修复”。不因用例/截图/提交数量多而宣称功能完成。

工具前导已识别本机gstack 1.91.268.0、遥测off；同时提示可升级及遥测偏好。此子任务不替用户同意遥测，不修改全局偏好/升级工具。实际产品QA由主控按当前已授权范围继续；该工具偏好不影响本静态文档完成。
