# MCP 存储排队期间的授权与预览复查

日期：2026-10-27。本片是共享服务/真实 RxDB/Node loopback 的 C 与 B/S 验证，**不是 Native MCP 连接实现或手机 SDK 验收**。

## 首次失败与根因

现有 `RxdbMcpAssetStore` 已支持在实际 modifier 内执行 `assertCanCommit`，但直接 `McpAssetService` 调用没有提供该回调。初始授权检查与真正存储提交之间可以排队；撤销或五分钟预览过期后，旧请求仍能写入。Web 桥有自己的撤销围栏，但没有把本次精确预览的检查贯穿 `/check-write`。

| 执行步骤 | 预期 | 原实际 | 修后实际 |
|---|---|---|---|
| 授普通项目 name 写权限→建立并批准精确预览→暂停实际 RxDB modifier 第3/第4次写前检查→撤销→恢复 | 旧名称保持，请求拒绝，无 applied 回执 | 两种时序均返回 applied 并改名 | 两种均 grant-denied，原名称保持；pending 保守保留，不自动重放 |
| 同上，暂停后仅推进 authority 时钟使预览过期，grant 本身仍有效 | 旧预览不能提交 | 两种时序均 applied | 两种均 preview-not-approved，原名称保持 |
| 使用真实 Node loopback、BrowserMcpBridgeClient 与 RxDB，批准后暂停实际 modifier→预览过期→恢复 | Web 桥也要在同一写尝试复查精确预览 | 直接服务修复后，此路径仍 applied | owner 内的原回调经 `/check-write` 被执行，拒绝写入；没有把函数/审批接口发送给客户端 |
| 直接 list/get/preview 读取暂停→撤销→返回读取结果 | 不再把普通资料或可用预览交给已撤销请求 | 三种均返回结果 | 三种均 grant-denied，原资料不变 |

不是通过删掉入口、改变 grant 范围、修改 TTL 或缩短等待时间解决。C 用显式 gate 控制先后顺序；预览过期仅推进隔离 authority 时钟，不改主机时钟。

## 修复与验证证据

- `service.ts` 在数据释放前复查授权，并向存储传入每次提交尝试的授权与原精确预览复查。实际 CAS、字段白名单、幂等 operationId 与不确定 pending 策略保持。
- `bridge.ts` 仅在 trusted pending 结构保存该回调，现有 `/check-write` 执行；之后再次检查该 pending 是否仍有效。客户端不能提供或替换回调，不增加 MCP 工具或新的批准路由。
- 原红：`test-results/mcp-direct-authority-red.json` 四条；`mcp-direct-read-red.json` 三条；`mcp-approval-bridge-red.json` 一条。原实际均有返回数据或 applied 的断言证据，未用超时冒充业务失败。
- 最终六个受影响合同文件 42项、0失败/跳过；`test-results/mcp-authority-bridge-final.json`。包括原有撤销围栏、请求期限、未知写入不重放、正式工具注册、CAS 与投影合同。类型检查和四个所改 TS 文件 lint 均通过。
- 另从正式 Web UI 对独立官方 SDK stdio 客户端执行授权、读取、逐次精确审批、写入与撤销相邻链，1项18.5秒通过；`test-results/mcp-direct-authority-web.log`，截图/权威回执在相邻 evidence。不是只有模拟服务反馈或按钮可点。
