## 实际原红与根因

先跑英文项目最小链：甲保留旧名称/备注草稿 → 乙真实 UI 保存 → 甲 Save 正确拒绝且保草稿 → 甲取消、重读、明确再保存成功。随后甲打开 Delete 确认 → 乙再次正式 UI 改名/备注 → 甲确认删除。**实际直接返回项目列表，没有冲突提示；回读乙的新名称/备注仍在但 `deleted:true`。** 不是仅错误定位器没找到。

固定原件：`test-results/mobile-ordinary-stale/red-with-final-output/mobile-ordinary-stale-acce-3b592-Pages-stale-edit-and-delete/`。合成 ID `84ece066-f258-4863-abf8-f0bd4872e560`，`final-observed.json` 保留 `B newer before delete project` / 对应新备注和 `deleted:true`，失败截图显示列表。最小复现和后续完整原红均保留，没有修改旧判定。

在修产品前，同一冻结消费者源的四类×两语八条也逐一执行；每条前半旧 Edit 拒绝、保稿及重读重试通过，均在旧 Delete 处失败。八个 `final-observed.json` 分别核到乙的新值与 `deleted:true`。这是一个共享删除链缺陷的八个条件，不算八种 bug。

根因：原 `apps/web/src/page-asset-detail.tsx:715–723` 的 `confirmDelete` 仅调用 `deleteEntity('asset', asset.id)`，两个 Delete 打开入口未固定完整 Asset；`packages/local-db/src/index.ts:1549` 的旧 ID 接口会重新读取最新 current 再删。仓库保护的是其刚读取的版本，没有验证用户打开确认时的版本，导致 UI 的旧确认失效。

## 修复范围

经主控确认所有权后只改两处生产源：

- `packages/local-db/src/index.ts` 新 `deleteAssetIfCurrent(expected)` 薄接口：校验完整 Asset、拒绝已经 deleted/purged 的输入 → 原 renewal 锁 → 原 `settleRenewalJournals` → 原 `saveAssetIfCurrent` 的最终 payload CAS 和 tombstone。沿用附件存在、分类/恢复/历史门槛，未在 UI 比较后再删最新版本。旧 `deleteEntity(type,id)` 保留原兼容行为及已删除幂等。
- `apps/web/src/page-asset-detail.tsx` 两个打开入口都 `structuredClone(asset)`；Confirm 仅使用该 base，资料更新不替换确认依据。pending 保留原 in-flight 直到结束，关闭/取消/Confirm 禁用，Escape 不关闭。每个 route scope 有独立生命周期，旧 route 完成或失败不导航/提示/关闭新页面；取消再开才抓取新快照。复用既有 `assetDeleteStale` 双语文案和 Dialog，不改布局、schema 或协议。
