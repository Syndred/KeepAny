# 07 商业项目拆分与托管边界

## 当前决定（2026-10-11）

采用**完整本地核心开源＋未来可选付费托管**。当前先整理并验证本地测试版，暂停扩展会员、支付、官方云服务及运营功能。已有商业实现与实验联调不代表服务已开放；本仓库的试用不需要商业账号。

付费方向是托管、存储、自动备份、可靠通知与运维支持。本地资料管理、密码库、关系、备份及完整导出不以付费为条件。未来服务是否上线、提供哪些范围，以生产验收和公开条款为准，不预设上线日期。

## 独立仓库

```text
KeepAny/      开源本地核心、用户资产 UI、集成与同步基础源码
KeepAnyAdm/   独立商业仓库：官网、会员、付款、运营后台
```

KeepAnyAdm 已使用单独购买的 ShipAny 模板。模板源码不复制到 KeepAny，也不随开源便携包或自部署包分发。文件夹和 HTTP 分离不能替代各自的许可证检查。

| 能力 | KeepAny | KeepAnyAdm |
|---|---|---|
| 资产、分类、关系、待办、密码库、导出 | 完整本地核心 | 不复制，不提供运营查看入口 |
| 基础同步协议与服务、自带模型、MCP | 开源源码，按验证状态提供 | 未来可选托管与运营 |
| 官网、产品介绍、定价与营销邮件 | README 与开源文档 | 使用商业仓现有模板 |
| 付款、订单、配额与客服权限 | 仅消费明确授权的服务权益 | 在独立商业服务管理 |
| 用户资料内容 | 本地管理；同步遵循独立加密边界 | 运营后台不得直接浏览个人内容 |

“后台”指运营后台，不是把用户资料详情搬进模板。收费不能控制本地 CRUD，商业服务不因此取得用户资料的解密密钥。

## 保留的架构边界

- 核心本地无需注册；自部署身份由用户自己的同步服务管理。
- 官方账号与会员建立显式绑定，不因相同邮箱自动合并，不跨域共享数据库 cookie。
- 商业权益与资料解密分开；短期限定用途的权益凭证由同步服务验证签名、期限与撤销。
- 付款 webhook 须验签与幂等；浏览器成功页不是已付款凭证。
- 数据库、密钥与迁移独立；运营人员仅接触必要的订单和使用量。
- 官方官网、应用和同步可使用独立域名；只写实际取得并部署的地址。

已有本机合成账号及固定提交联调，只证明对应软件路径。真实账号、设备、对象桶、HTTPS、部署、安全、计费与取消到期验收须单独完成；未完成前不向用户宣称官方服务可用。

## 恢复扩展前的条件

先验证陌生用户能独立完成“项目→关联账号→订阅→维护待办→下载备份→干净环境恢复”，收集录入与查找成本、失败点及持续使用反馈。之后再决定哪项托管服务值得收费，避免先扩大商业范围。

商业仓继续开发时，优先沿用实际模板的实现与许可范围，不把核心的技术选型强加给商业模板。两个仓库保持 zh-CN/en 术语一致，各自记录提交、推送、部署和验收状态。

ShipAny 的模板分发与协作须符合已购许可证；AGPL 核心的义务独立履行。当前没有因仓库拆分而完成整体法律兼容性结论。上游入口：[ShipAny 许可证](https://shipany.ai/license)、[模板文档](https://docs.shipany.ai/shipany-tanstack)。
